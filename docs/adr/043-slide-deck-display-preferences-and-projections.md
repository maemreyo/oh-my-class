# ADR-043: Slide Deck Display Preferences and Projection Boundaries

## Status

**Proposed** (2026-07-07) — Extends ADR-040 and ADR-042 with production display preferences, presentation/print separation, student-safe chrome policy, and UI/UX rules for standalone slide-deck HTML and app preview.

## Context

The native `slide_deck` artifact now has a canonical content model, renderer projection seam, and initial standalone HTML surface. The next production hardening pass must address teacher feedback that the deck needs customizable print behavior, crisp print borders, and less robotic student-facing chrome such as visible “Generated by oh-my-class” header/footer text.

These concerns are not content-generation decisions. They are presentation, projection, and teacher workflow decisions. If they are patched directly into the current template, student safety, standalone HTML behavior, app preview behavior, and export reproducibility will drift. The system needs a typed, modular display-preference seam that lets the app and standalone HTML control display without allowing the LLM to decide layout or student-facing chrome.

Relevant constraints:

- The canonical teaching-pack lifecycle remains authoritative.
- `SlideDeckData` remains the content model; surfaces are projections from that model.
- Student-facing HTML must not contain teacher notes, answer keys, hidden answer data, or scrapeable teacher-only fields.
- Standalone HTML must remain offline-capable with no CDN or external assets.
- Print must show the full deck, not only the active presentation slide.
- UI/UX must be classroom-ready, readable, keyboard-accessible, and responsive.

## Decision

1. **Presentation is primary; print is a separate projection.** Slide decks are optimized for screen teaching first. Print behavior is not a CSS afterthought over the active slide; it is a projection with its own layout rules.
2. **Five surfaces are recognized.** The production model distinguishes:
   - `presentation`: screen teaching, slide navigation, clean chrome, no teacher-only content.
   - `student`: safest share surface, no teacher-only content, no robotic provenance chrome.
   - `teacher`: teacher preview/control surface with notes and metadata outside the student canvas.
   - `print`: browser-print/PDF handout surface, all slides visible, controls hidden.
   - `review`: internal quality/compliance projection optimized for deterministic scanning.
3. **Display preferences are typed and slide-deck-specific.** Introduce a `SlideDeckDisplayPreferences`-style contract rather than loose metadata keys or a generic artifact-wide abstraction. The first version is slide-deck-specific and can be generalized only after another artifact proves the same abstraction is needed.
4. **Preferences use a hybrid persistence model.** The artifact carries safe defaults, app preview may provide runtime overrides, and export records effective settings. Standalone HTML may support query/hash overrides plus namespaced localStorage, but content remains safe if storage is unavailable.
5. **The LLM does not choose display preferences.** The app, gateway, renderer, and typed defaults own `surface`, `printLayout`, `slidesPerPage`, `chrome`, and future paper settings. Generated content never decides whether answer-bearing or teacher-only data is visible.
6. **Student-facing branding is minimal.** Student and presentation surfaces must not show “Generated by oh-my-class” as persistent classroom chrome. Teacher/review surfaces may show clear provenance. Print may include a small footer only when the teacher explicitly enables it.
7. **Print v1 supports paged and continuous layouts.** The initial production print modes are:
   - paged grid with `slidesPerPage: 1 | 2 | 4 | 6`;
   - continuous vertical slide cards.
   Teacher-notes print, paper size/orientation controls, worksheet projection, native PDF, and PPTX remain future work.
8. **Print slides remain aspect-locked.** Print cards preserve a 16:9 slide boundary using layout sizing, not transform scaling. This avoids blurry borders and text.
9. **Border crispness is a rendering-correctness requirement.** Print mode must avoid transform scaling, opacity-only borders, filters, shadows, and nested rounded-border owners that blur corners. Screen mode may use subtle polish, but print uses solid crisp borders.
10. **Standalone controls are teacher-friendly but restrained.** V1 standalone controls include previous/next, keyboard navigation, progress, print button, print layout selector, and chrome toggle only when the surface permits it. Thumbnails, timers, speaker-note printing, and staged reveals are deferred.
11. **App preview uses a split model.** The main canvas defaults to presentation view. Teacher notes, quality status, metadata, and print/share controls live in side or collapsible panels. A `Print & sharing` panel exposes surface, layout, slides-per-page, and chrome options.
12. **Accessibility target is classroom-ready.** V1 must provide semantic headings, labeled controls, visible focus, keyboard navigation without focus traps, reduced-motion support, readable projector/mobile/print layouts, and no color-only meaning.
13. **Responsive behavior is hybrid.** Tablet/desktop/projector views keep the 16:9 canvas. Mobile uses readable stacked slide cards rather than microscopic scaled slides. Print remains independent.
14. **Motion is subtle and optional.** V1 may use opacity/transform transitions only, respects `prefers-reduced-motion`, and disables motion in print. Staged bullet reveals and animated diagrams are future work.
15. **Theme integration derives slide tokens from existing theme tokens.** `theme.json` remains the source of truth. Slide-specific CSS variables may express component tokens such as border, radius, print gutter, progress color, and print contrast.

## Consequences

- The slide deck becomes safer and easier to evolve because content, projection, display preferences, app preview, standalone controls, and quality review have explicit boundaries.
- Teachers get flexible print and sharing options without requiring deck regeneration.
- Student-facing decks become cleaner and less AI/robot branded by default.
- Print quality improves because the system avoids transform-based scaling and ambiguous border ownership.
- The renderer, gateway preview/export routes, and web preview component must understand effective display preferences instead of hardcoding one template behavior.
- Future features such as teacher-guide print, paper size, speaker notes, thumbnails, timers, native PDF, and PPTX have clear extension seams.

## Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| Typed slide-deck display preferences (chosen) | Safe, explicit, testable, avoids over-generalization | Requires contract, projection, renderer, gateway, and UI wiring |
| Patch current template CSS | Fast | Brittle; mixes surfaces; hard to test; likely leaks chrome or teacher data |
| Let LLM generate print/chrome choices | Flexible prompt surface | Violates SoC, makes exports non-deterministic, risks student safety |
| Generic artifact display preferences now | Potential reuse | Premature abstraction without a second artifact needing it |
| Student branding fully visible | Marketing/provenance | Classroom UX feels robotic; distracts students |
| Hide all provenance everywhere | Cleanest student view | Weak teacher/admin traceability and Layer-3 brand-string expectations |
